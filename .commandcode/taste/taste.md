# Taste
- Wants to manually try the app (via browser/Laragon) before new features are built — explicitly pauses feature work ("ntar dlu buat fitur baru nya. sekarang aku pengen nyoba manual dlu") and asks how to run/test the current state; also actively tests the running app after changes and reports bugs found with concrete examples (e.g., close button on the receipt card only refreshed instead of closing; admin report page showing 16.35 when local time was 23.35). Confidence: 0.9
- Prefers a ready-made seed script with demo data (demo accounts with credentials, sample products/categories/suppliers/discounts) so the app can be manually tested right away — chose `database/seed.php` over manually inserting rows via phpMyAdmin; expects the demo accounts (admin/admin123, kasir/kasir123, and the member demo with its MEM-number + member123) to always be present and usable for manual login testing — reported login failing when a test run had wiped the users table (recurred until e2e was made to auto-restore seed data at the end) and again when the demo member login didn't work. Confidence: 0.95
- Demo/testing credentials must be self-discoverable on the login page itself and fetched dynamically from the DB rather than hardcoded — seeded identifiers (e.g., member numbers MEM-XXXXXX) change on every seed re-run, so a hardcoded demo number silently breaks the demo login; the accepted fix shows the current demo account's number/phone/password right on the page and accepts member number, phone, OR name as the login identifier so manual testing is frictionless. CRITICAL CONSTRAINT: demo hints may only ever show clearly fictional dummy data (a seeded dummy account or static generic text) — pulling real member records (name, member number, phone) from the DB to display on a public login page was flagged as a serious privacy breach. Confidence: 0.7
- Reports bugs as terse symptom statements with no details (e.g., "ada pop up datatables warning", "akun kasir dan admin ga bisa lagi", "error tu halaman transaksi") and expects the assistant to autonomously reproduce, diagnose the root cause, fix, verify (curl + e2e), and push the fix without asking clarifying questions — even when the follow-up is equally terse, the assistant is expected to trace what the user actually did (URL, page, action) rather than ask for specifics. Confidence: 0.95
- When a user reports a blank white screen ("layar nya malah putih semua"), do not assume a server error — verify the HTTP response first: a 200 with full HTML from the server means the problem is client-side, and it is not always CDN/cache: after CDN assets were vendored locally AND the user switched browsers (ruling out stale cache), the white screen persisted because a Bootstrap `d-none` (display:none) was applied to the entire content column when a state precondition (no active open-cash shift) wasn't met — hiding even the "Buka Kas" form that should have appeared; diagnose rendering issues in a real browser (screenshot + DOM inspection of classList/computed display/sizes) rather than concluding from curl alone. Confidence: 0.85
